# QA LLM Assistant

## 1. Назначение

Проект автоматизирует рутинные задачи QA-инженера, связанные с подготовкой тестовой документации. Реализованы три независимых режима работы:

1. **Генерация тест-кейсов** по запросу пользователя на основе существующих кейсов, общих шагов и проектной документации.
2. **Поиск** тест-кейсов в базе знаний с последующим ручным редактированием или неиронным обновлением по запросу.
3. **Диалог с языковой моделью** для получения справочной информации на основе проектной документации.

Реализована синхронизация с TestOps: тест-кейсы загружаются в базу знаний и выгружаются обратно в TestOps по подтверждению пользователя.

## 2. Термины

- **Векторный поиск** — способ поиска, при котором каждому элементу (тест-кейсу, фрагменту документации и т. д.) ставится в соответствие эмбеддинг — числовой вектор, отражающий смысл элемента через его положение в n-мерном пространстве.
- **Плотный (dense) поиск** — векторный поиск: эмбеддинг запроса сравнивается по косинусной близости с эмбеддингами элементов базы, хранящимися в pgvector. Хорошо улавливает общий смысл запроса, но хуже работает с точными формулировками и специфическими терминами.
- **Разреженный (sparse) поиск** — фразовый полнотекстовый поиск в OpenSearch: слова приводятся к начальной форме (лемматизация) и ищутся по обратному индексу. Хорошо находит точные формулировки, но не учитывает общий смысл текста.
- **Реранкер (cross-encoder)** — отдельная модель, оценивающая релевантность конкретного найденного кандидата запросу пользователя. Применяется после первичного, более дешёвого поиска, чтобы уточнить порядок результатов.
- **База знаний** — совокупность документации, тест-кейсов и переиспользуемых шагов проекта, из которой для каждого запроса подбираются наиболее релевантные фрагменты для контекста языковой модели.

## 4. Пользовательские сценарии

- **Чат.** Запрос (текст + до 5 изображений) → контекст собирается из документации, тест-кейсов и общих шагов → ответ языковой модели. В базе сохраняется только история сообщений;
- **Поиск по базе.** Режим определяется по кавычкам в запросе (dense / phrase / cascade) → найденные тест-кейсы отображаются в панели. Далее возможно:
  - просмотр без изменений;
  - ручное редактирование;
  - обновление отмеченных кейсов моделью по новому техническому заданию.

  В любом из вариантов отмеченные кейсы можно экспортировать в TestOps.
- **Генерация чек-листа.**
  1. Перед генерацией база знаний проверяется на наличие существующих в системе кейсов (оценка реранкера выше порога).
  2. Если совпадение найдено — генерация не запускается, пользователю возвращаются найденные кейсы; дальнейшая работа с ними идёт по сценарию «Поиск по базе».
  3. Если совпадений нет — контекст собирается из базы знаний, и языковая модель генерирует новый чек-лист с нуля.
  4. Над сгенерированным чек-листом доступны: ручное редактирование и сохранение; дополнение новыми кейсами по уточнённому ТЗ; обновление отмеченных кейсов моделью (в этом случае модель вправе предлагать новые кейсы); экспорт выбранных пользователем кейсов в TestOps.
- **История чатов.** Позволяет открыть содержимое предыдущих чатов с функциональностью, соответствующей их типу (чат, поиск или генерация).

## 5. Поиск по базе знаний

В проекте используются два независимых механизма извлечения информации.

### 5.1. Пользовательский поиск (`rag/search_pipeline.py`)

Используется эндпоинтом (сценарием) поиска по базе и проверкой на готовые кейсы перед генерацией. Режим определяется синтаксисом запроса:

1. Запрос без кавычек — только плотный (векторный) поиск.
2. Запрос целиком в кавычках — только разреженный (фразовый) поиск.
3. Смешанный запрос — каскад: сначала разреженный поиск по содержимому кавычек отбирает подмножество кандидатов, затем плотный поиск ранжирует это подмножество по свободным словам запроса вне кавычек.

Технические детали:

- **Плотная ветка:** эмбеддинг запроса и поиск по косинусной близости в pgvector среди `SEARCH_CANDIDATE_POOL` (по умолчанию 50) кандидатов, после чего реранкер отбирает `SEARCH_TOP_K` (по умолчанию 25) лучших и отсекает результаты ниже порога `SEARCH_MIN_RERANK_SCORE`.
- **Разреженная ветка:** фразовый поиск в OpenSearch с поддержкой многоточия внутри кавычек через позиционные разрывы — позволяет задать относительный порядок слов, не требуя, чтобы они шли подряд.

### 5.2. Извлечение контекста для чата и генерации (`rag/hybrid_search.py`)

Контекст, который попадает в промпт языковой модели при диалоге и при генерации чек-листа, собирается отдельным механизмом — слиянием рангов плотного и разреженного поиска (Reciprocal Rank Fusion) по каждой категории базы знаний (`docs`, `examples`, `shared_steps`). Результат отфильтровывается по относительному порогу от лучшего результата выборки (индивидуальному для каждой категории). Реранкер в этом механизме не используется — это самостоятельный путь извлечения контекста, отличный от пользовательского поиска, описанного в разделе 5.1.

## 6. Генерация чек-листа

1. Пользователь отправляет техническое задание (текст и, опционально, изображения, раздел, вид, количество требуемых кейсов).
2. База знаний проверяется на наличие готовых кейсов (раздел 5.1); при совпадении выше порога генерация не запускается.
3. Иначе контекст, собранный по механизму раздела 5.2, включается в промпт и отправляется в Ollama с требованием ответа по JSON-схеме.
4. Режимы `generate` / `extend` / `update` отличаются входными данными: `generate` стартует с нуля, `extend` и `update` получают на вход уже существующий чек-лист.

## 7. Диалог

Запрос пользователя обрабатывается тем же способом извлечения контекста, что и при генерации чек-листа (раздел 5.2); системный промпт диалога соответствует режиму чата.

## 8. Синхронизация с TestOps

Тест-кейсы и общие шаги загружаются через REST API Allure TestOps, сохраняются в базе данных и индексируются обоими видами поиска. Экспорт отмеченных кейсов выполняется в указанную папку TestOps по числовому пути вида `n.n.n`.

## 9. Загрузка документов в базу знаний

Загрузка через веб-интерфейс реализована в меню пользователя, в разделе "Документы".

Реализована возможность выбрать на компьютере пользователя .doc файл и загрузить его в базу данных, в момент выбора происходит сверка наименования файла: если присутствует документ с аналогичным наименованием - высвечивается предупреждение. После загрузки документа, он сразу же индексируется

Реализована возможность скачать/удалить определенный документ из базы по клику на соответствующую кнопку.
